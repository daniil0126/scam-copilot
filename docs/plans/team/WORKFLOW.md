# Как работаем

Цель: никаких конфликтов, предсказуемый ритм. Планы: [../00-ROADMAP.md](../00-ROADMAP.md). Личные файлы: [daniil](daniil.md), [denis](denis.md), [adil](adil.md), [ruslan](ruslan.md).

## 1. Владение кодом (кто что трогает)
| Зона | Владелец | Остальные |
|---|---|---|
| `backend/app/models.py`, `db.py`, `main.py`, `paypal.py`, `oauth.py`, миграции, очередь | Даниил | только через PR к нему |
| `backend/app/rules/`, `scoring.py`, `checks.py` | Адиль | Даниил подключает, не меняет логику |
| `backend/app/llm.py`, `chat.py`, `notifications/`, `reports/`, `backend/tests/dataset/`, `docs/` | Руслан | |
| `src/` | Денис | backend-изменения не вносит |

Чужую зону не правим. Нужно изменение: issue или сообщение владельцу, он делает или ревьюит PR.

## 2. Контракты как единственный источник правды
- `docs/plans/contracts.md` (создаёт Даниил в первые 2 дня): `Invoice`, `Signal`, `RiskResult`, формы API, образцы JSON.
- Изменение контракта только отдельным PR с пометкой `contract`, одобрение всех четверых. Старые поля не удаляем, добавляем новые (обратная совместимость).
- Версия контракта в заголовке файла; Денис и Руслан используют образцы JSON как фикстуры.

## 3. Git
- `main` защищён: прямых пушей нет, merge только через PR, минимум 1 ревью, зелёные проверки.
- Ветки: `feat/<план>-<кратко>` (пример `feat/04-duplicate-rule`), живут не дольше 2–3 дней.
- PR маленькие (до ~400 строк), один подплан или его кусок. В описании: что изменено, как проверено, что осталось.
- Squash merge. Перед PR: `git pull --rebase origin main`.
- Коммит и пуш делает автор; ИИ-ассистент ничего не коммитит без явной просьбы.
- Миграции БД: только Даниил или PR к нему, один человек, чтобы не было двух голов Alembic.
- Не коммитить: `.env`, `key.pem`, `*.db`, `dist/`, `node_modules/`.

## 4. Проверки перед PR (обязательно)
- Backend: `cd backend && pytest`.
- Frontend: `npx tsc -b` и `npx eslint .`.
- Новый код с тестами. PR без тестов к правилам, нормализации и очереди не принимается.
- Желательно CI (GitHub Actions) с этими тремя командами; настраивает Руслан.

## 5. Ритм
- **Ежедневно, 10 минут (чат или звонок):** сделал вчера, делаю сегодня, что блокирует.
- **Конец каждой фазы:** демо на Sandbox, гейт из ROADMAP, короткий отчёт: что изменено, какие тесты пройдены, какие проблемы остались.
- **Ревью-SLA:** первый ответ на PR в течение полусуток. Блокирующие PR (контракты, схема БД) ревьюятся в первую очередь.
- **Доска задач:** одна колонка на подплан (Todo / In progress / Review / Done), у каждой задачи один владелец.

## 6. Зависимости и порядок
```
Даниил: контракты (день 1–2) ─┬─> Денис (фикстуры -> UI)
                               ├─> Адиль (rules на фикстурах)
                               └─> Руслан (dataset, метрики, AI)
Даниил: 03 -> 02 -> 08 ─ подключает ─> evaluate() Адиля ─> 09 ─> алерты Руслана
```
Никто не ждёт чужую реализацию: работаете на контракте и фикстурах, интеграция на фазовых гейтах.

## 7. Принципы качества (из ТЗ)
- Evidence over assumptions. Не придумываем поля PayPal и результаты анализа.
- Нет фиктивных данных в интерфейсе. Dev-фикстуры не попадают в сборку.
- «Признаки» и «требует проверки», не «мошенничество».
- Только анализ: никаких платежей, отмен и изменений инвойсов.
- Секреты только в `.env` на backend.

## 8. Эскалация
Блокер дольше полусуток, спор о контракте или архитектуре: пишете Даниилу, решение фиксируется короткой ADR в `docs/plans/adr/`.
