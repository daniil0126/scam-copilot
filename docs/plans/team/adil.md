# Адиль: Rule Engine

**Подпланы:** 04, 05, 06. Правила команды: [WORKFLOW.md](WORKFLOW.md). (Если вы с Русланом поменялись ролями, файлы переставьте.)

## Ответственность
- Правила A–E, оценка риска (score, level, confidence, рекомендации), дубликаты, профили поставщиков.
- Код живёт в `backend/app/rules/` и `scoring.py`. Это чистые функции без сети, БД и AI.
- Не трогаете `models.py`, `main.py`, миграции: данные получаете через аргументы.

## Интерфейс (контракт от Даниила)
```
evaluate(invoice: Invoice, history: VendorHistory, config: RulesConfig) -> RiskResult
```
`history` готовит Даниил; формат профиля поставщика согласуете в `contracts.md`.

## Задачи
| Этап | Задачи |
|---|---|
| 1 | Скелет пакета `rules/`, тип `Signal` (type, severity, evidence, source, rule_version), конфиг порогов |
| 2 | Правила: A (сумма, `INSUFFICIENT_DATA`), D (ссылки без перехода), C (подмена поставщика) |
| 3 | Правило B (Exact/Potential/Similar), E (активность отправителя) |
| 4 | Агрегация в 05: убывающий вклад коррелирующих сигналов, confidence отдельно от score, рекомендации по шаблонам |
| 5 | 06: кластеры дубликатов, история изменений контактов, связи между отправителями (только при 2+ независимых совпадениях) |

## Правила качества
- Каждое правило: срабатывает / не срабатывает / мало данных / поля `null`. Тесты в `backend/tests/test_rules_*.py`.
- Сигнал без evidence не создаётся. Неизвестное поле не меняет score, но снижает confidence.
- Адаптируйте существующий `checks.py`/`scoring.py`, не создавайте параллельную реализацию.
- Пороги пометьте как начальные: калибровка с Русланом на тестовом наборе.

## Готово, когда
Все пять правил работают без сети и AI, любой score раскладывается на сигналы с evidence, тесты зелёные.
