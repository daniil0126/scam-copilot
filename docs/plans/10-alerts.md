# 10. Алерты

**Приоритет:** P1. **Раздел ТЗ:** 15.4. **Зависит от:** 05, 09.

## Цель
In-app уведомления о значимых находках с расширяемой архитектурой каналов.

## Задачи
- [x] Категории: Critical Risk, High Risk, Potential Duplicate, Vendor Impersonation, Suspicious Payment Link.
- [x] Настраиваемые пороги и включение категорий на аккаунт (таблица настроек).
- [x] Содержимое уведомления: Invoice ID, Risk Level, время обнаружения, главные сигналы, ссылка на карточку анализа.
- [x] **Дедупликация:** уникальный ключ `account + invoice_version + event_type`; повторная обработка не создаёт второе уведомление.
- [x] Интерфейс канала `NotificationChannel` (сейчас реализован `InAppChannel`; email и browser notifications добавляются без изменения ядра).
- [x] API: список, отметка прочитанным, счётчик непрочитанных. Расширение опрашивает backend (опционально значок на иконке).
- [x] Формулировки: «обнаружены признаки», а не «мошенничество».

**Статус (2026-11-01):** код в `backend/app/notifications/`, подключён в `monitor.py` (после проверки версии инвойса) и `main.py` (роутер). Тесты: `tests/test_notifications.py`. Тесты (категории; одно уведомление на версию, повтор, новая версия, отключённая категория, чужой аккаунт, новый канал) проходят: `cd backend && .venv/bin/python -m pytest -q` даёт 302 passed (проверено 2026-11-01 после мерджа PR #4–#11). Изменение порогов пишется в аудит-лог. Остаётся экран уведомлений и значок (Денис). Таблицы `notifications` и `alert_settings` лежат в `notifications/models.py`; их перенос в `models.py` и миграцию согласовать с Даниилом.


## Тесты
Порог пересечён: 1 уведомление; повторная обработка: 0 новых; изменение инвойса: новая версия даёт новое уведомление; отключённая категория.

## Готово, когда
High/Critical инвойс создаёт ровно одно уведомление со ссылкой на детали.
