# 04. Rule Engine

**Приоритет:** P0. **Раздел ТЗ:** 4. **Зависит от:** 03.

## Цель
Независимый от AI модуль правил. Принимает нормализованный инвойс и контекст истории, возвращает список сигналов.

## Контракт сигнала
`type, severity, evidence (конкретные значения), source (API | RULE_ENGINE | AI), rule_version`. Сигнал без evidence не создаётся.

## Правила
- [ ] **A. Unusual Amount.** Сравнение с историей того же отправителя (среднее/медиана, разброс). Порог минимальной истории (например 3 инвойса, конфигурируемо), иначе статус `INSUFFICIENT_DATA`. Рост сам по себе не улика.
- [ ] **B. Duplicate** (первая версия: по одному аккаунту). Exact / Potential / Similar по ID, номеру, отправителю, сумме+валюте, позициям, близости дат. Совпадение одной суммы не даёт дубликат. Расширение в плане 06.
- [ ] **C. Vendor Impersonation.** Сравнение email/имени/контактов с историей: похожий домен, смена домена при том же имени и т.п. Только «несоответствие», не «мошенник».
- [ ] **D. Suspicious Link.** Разбор URL без перехода: IP вместо домена, punycode, глубокие поддомены, бренд в чужом домене, несовпадение с ожидаемым `paypal.com`. Внешний URL сам по себе не вредоносен.
- [ ] **E. Unusual Sender Activity.** Частота и объём инвойсов отправителя относительно его истории; учитывать объём истории.
- [ ] Каждое правило возвращает `INSUFFICIENT_DATA` вместо молчаливого «ок».
- [ ] Правила конфигурируются (пороги в одном месте), версия набора правил записывается в анализ.

## Файлы
Новый пакет `backend/app/rules/` (по модулю на правило), использует и расширяет `checks.py`; не дублировать существующие проверки, а перенести/обернуть.

## Тесты
Таблица кейсов на каждое правило: срабатывает / не срабатывает / мало данных / отсутствующие поля.

## Готово, когда
Все пять правил работают без сети и без AI, покрыты тестами, не падают на `null`-полях.
