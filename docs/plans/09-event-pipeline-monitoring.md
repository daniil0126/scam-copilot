# 09. Event pipeline, очередь и непрерывный мониторинг

**Приоритет:** P1. **Разделы ТЗ:** 15.2, 15.3. **Зависит от:** 08.

## Цель
Автоматическая обработка новых и изменённых инвойсов на backend, независимо от того, открыто ли расширение.

## Задачи
- [ ] **Очередь** в БД (таблица `jobs`: `status, attempts, next_run_at, idempotency_key, error`) и воркер в процессе backend. Без Redis/Celery, пока не доказана необходимость.
- [ ] Конвейер на задание: validate → normalize → проверка версии → rules → cross-invoice → AI (если нужно) → score/confidence → сохранить → алерт (план 10).
- [ ] **Идемпотентность:** уникальный ключ `account + invoice + content_hash`; повторная обработка не создаёт дублей результатов и алертов.
- [ ] Retry временных ошибок с exponential backoff, лимит попыток, затем статус `failed` без блокировки остальных.
- [ ] **Polling** каждые 5 минут (конфиг), планировщик в backend (APScheduler или встроенный цикл); учёт rate limits.
- [ ] **Webhooks:** проверить доступные события Invoicing; если подходят, добавить эндпоинт с верификацией подписи PayPal; иначе остаться на polling (решение в ADR плана 01).
- [ ] Обнаружение пропущенных периодов: если разрыв с чекпоинта больше интервала, запустить догоняющую синхронизацию.
- [ ] Пауза/возобновление мониторинга на аккаунт; ручной sync.
- [ ] Восстановление после падения: задания `running` старше таймаута возвращаются в очередь при старте.

## Тесты
Двойная доставка одного события, падение воркера посреди задания, 429 при sync, пропуск окна и догон, пауза.

## Готово, когда
Новый инвойс в Sandbox анализируется без клика пользователя, а перезапуск backend не теряет и не дублирует задания.
