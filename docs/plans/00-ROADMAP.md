## Конфликты и риски, которые решить на этапе 01

1. **Чужой счёт через API недоступен.** По `docs/ROADMAP.md` проверено: счёт другого аккаунта даёт `403 NOT_AUTHORIZED`. Новое ТЗ анализирует инвойсы *авторизованного* аккаунта (то есть выставленные им). Это другой сценарий, чем «жертва получила счёт от мошенника». Решение: заявить в README/Submission честно, что мониторинг и Batch Audit работают для счетов подключённого аккаунта, а путь плательщика остаётся через парсер страницы.
2. **Тип авторизации.** `GET /v2/invoicing/invoices` и `search-invoices` надо проверить по документации PayPal: какие работают с client credentials, а какие требуют токен пользователя (Log in with PayPal, scope). От этого зависит объём плана 02.
3. **Webhooks.** Проверить, есть ли события Invoicing (создание, обновление, оплата) и можно ли их верифицировать в Sandbox. Иначе polling (план 09).
4. **Хранилище.** Сейчас SQLite (`backend/scamcopilot.db`, SQLAlchemy). Очередь делаем таблицей `jobs` и фоновым воркером в процессе backend, без Redis/Celery.
5. **Принято решение по конфликтам** из overlap-analysis: результат AI не входит в score (AI-находки показываются отдельно); перезапись `checks` заменяется версиями (горизонт B), пока `checks` обслуживает старый экран; кнопка «Check all invoices» превращается во вкладку Batch Audit, а не удаляется.
6. **Масштаб.** ТЗ крупное. План 12 и часть 06 (связи между отправителями) режутся первыми, если время ограничено.
7. **Вне Chrome-расширения.** Мониторинг при закрытом расширении требует постоянного процесса backend (планировщик в нём).
